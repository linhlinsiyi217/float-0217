一、最高优先级：真正修复联网搜书与阅读链路
用户手机实测仍然完全无法使用。上一轮只是过滤规则检查，不能认为联网已修复。本轮必须定位断点并实际请求。
1. 从用户输入到搜索请求、后端书源、结果解析、书籍详情、目录、正文阅读逐层检查。先用现有接口复现，保留必要的状态码、书源名、请求耗时及错误摘要，不输出密钥、Cookie等隐私。
2. 区分：无匹配结果、书源超时、书源响应异常、鉴权/配置缺失、格式解析失败。不能把全部错误变成“没有这本书”，也不能用本地假数据冒充联网成功。
3. 中文检索规范化：处理空格、书名号、简繁体和常见标点；建立可维护的中英文别名映射，例如简爱/简·爱/Jane Eyre。仅对适合该书源的别名扩展查询，不把所有中文词无条件翻译为英文，更不能依赖每次调用大模型翻译。
4. 搜索来源解耦：按Provider/Connector接口管理现有书源；多个来源分别超时与报错，一个失败不阻断其他来源。去重保留来源及版本语言；避免迟到的旧搜索结果覆盖新结果。
5. 保留现有番茄/红果实验和连接能力，先查当前仓库及相关分支，不猜分支、不删除、不改为mock。没有可用正式正文接口时明确能力边界，不承诺任意书源全文可读。
6. 明确结果能力：有元数据、可看详情、可读正文是三件事。可读正文才显示可读；仅外链内容提供准确外链入口，不用无法工作的“阅读”按钮。
7. 可评估中文维基文库及Gutenberg目录来源，来源页面与官方说明见本文末尾。Gutendex属于目录API，不是中文搜索万能接口；公共演示实例不是可承诺稳定性的唯一依赖。选择项目适用的部署方式，不强行新增无法部署到现有环境的完整服务。
8. 验证至少：中文“简爱”“呐喊”、英文“Jane Eyre”、不存在的书名、书源失败、连续两次快速搜索。分别记录真实结果、语言、来源，以及详情/正文是否可用。没有中文译本时要标明英文原版，不能假装中文正文。

二、完整内置书库：联网失败时仍有真实书可读
用户同意加入公开书籍。首批目标6至10本完整作品，以中文经典为主。
候选：红楼梦、西游记、聊斋志异、呐喊、彷徨、朝花夕拾；如遇版本/来源问题可换同类适合的经典，并说明最终选书。英文经典作为补充，不拿英文填充中文书库指标。
1. 每本先确认具体版本、作者、来源与可再分发条件。公开页面可看不代表现代译本、注释、封面都可复制；正文、翻译和封面分别核对。保留适用的来源、许可说明，不自行抹去署名。
2. 实际获取完整正文和章节，不放几段样文或只放封面简介。预先整理成项目支持的章节JSON/TXT/EPUB等格式，做目录与文本完整性校验；章节资源按需加载，避免首页打包整套全文。
3. 书库提供真实书名、作者、版本、语言、目录、正文和来源；封面使用可用合法素材或书名排版，不能误用其他书封面。
4. 接入现有书城、搜索、书架、阅读器、收藏、阅读进度与继续阅读。不另造完全独立的一套演示阅读器。新增/重复收藏要正确去重，不清掉用户原有书架。
5. 数据与应用一同部署或存入已有可用静态存储，不把每次阅读都依赖外部网页抓取。明确内置资源可直接加载；若没有缓存完整正文，不宣称完全离线可读。
6. 搜索结果标注“内置”或具体联网来源。内置书库是兜底，不是替代联网修复。
7. 每本抽查开头、中间、末尾及章节跳转；测试进度保存后刷新仍正确。最终列出实际内置的作品和版本，未完成的书不得写成已内置。

三、书房内容分享到聊天：卡片与AI读取一起修
现象：用户把书籍或帖子发到聊天，出现“查看网页 HTTP 422”，错误中含SubmittedDataMalformedError、path=url及异常长域名；角色接着围绕失败开玩笑，实际看不到分享内容。
异常域名仅是定位线索，不是已确认根因；核对发送载荷、链接生成、URL解析、读取工具和角色上下文。
1. 书房内部分享使用结构化消息：版本、内容类型、稳定bookId/postId、标题、封面/作者、允许展示的摘要、剧透标记及必要上下文。字段名按项目实际模型设计，不仅发送一串链接。
2. 内部内容由真实存储/API按ID解析，按当前用户与角色权限读取。不要让外部网页抓取器抓本地SPA路由，也不要把中文标题自动拼成域名。
3. 卡片使用项目已有正式域名和实际路由回跳，不嵌入过时预览域名；核验带参数、编码和旧卡片兼容。点击卡片能回对应书籍或帖子，返回聊天后会话和输入草稿保持。
4. 角色得到可读取内容，不能只见标题或HTML空壳就宣称读完整本。帖子与书籍支持上下文范围：正文可用时按用户请求加载相关内容，长书按章/选段提供，不把整书无差别塞进每次对话。
5. 剧透帖子默认仅发送受保护的书名/提示或安全摘要；未获展示授权不得把隐藏正文送给角色或存入角色记忆。保持上轮剧透机制。
6. 内容读取失败显示简短可理解的提示和重试入口，技术详情收纳于详情面板；错误JSON不得当作正文交给角色，角色不得假装已经阅读。
7. 分享保留先预览、点击发送才发送、取消不发送的流程；只能发到选中的现有好友会话，防重复发送。
8. 实测普通书籍、普通帖子、剧透帖子、内容已删除、旧链接和请求失败。检查可见卡片、AI实际获得的内容、回跳三个环节。无真实模型凭据时只验证数据链路，明确模型试聊待验，不编造试聊成功。

四、书房默认主题：纯白为底，颜色只突出重点
现在多个主页面是大面积冷灰背景，不符合要求。
1. 默认主体背景#FFFFFF。黑/炭黑作为主要按钮与主文字，灰用于次文字、辅助按钮和分隔；不要把所有容器底色叠成灰蒙蒙一片。
2. 允许鲜明的绿色、紫色、黄色、蓝色作为分类、当前项、提示或重要状态。禁止荧光/霓虹发光效果、刺眼渐变和大面积多色混搭。颜色需保持文字可读，不只靠颜色区分状态。
3. 保留白色Liquid/Pearl Glass，但玻璃主要用于Dock、工具栏和浮层，内容区不全部厚重玻璃化。不要满屏胶囊。用户已有自定义壁纸、主题与夜间设置仍可用，不强制覆盖用户选择。
4. “我的”动态小卡片可用浅灰底与纯白主体形成层次。保留既有横滑、对齐、点击打开中央详情功能。
5. 审计书城、书架、书桌、抽卡、书友圈、我的及各面板默认底色；本轮调整统一主题，不擅自重新设计所有不在范围内的功能。

五、头像状态气泡：本轮位置与大小最终要求
现象：当前巨大气泡横跨头像和姓名上方；空状态“写点此刻的状态”撑起一整块区域，用户已反复要求缩小。
最终位置：气泡在头像左上方，靠近头像；尾巴轻轻压住头像边缘一点点。用户“左上角”指头像附近的左上位置，不要擅自把整个素材旋转翻转成另一种云朵。
1. 使用原有云朵素材轮廓和白色液态玻璃，不另外随意画大椭圆。资源优先使用仓库已有public/study-room/bubble/bubble-mask.png，核对是否为用户给的同款；素材直链见末尾。
2. 裁掉素材无效留白，再按云朵实际可见轮廓计算大小。气泡可见宽度建议约头像直径的1至1.25倍，作为起始比例；根据实际手机截图微调，不是对原始1600px图片直接设原尺寸。
3. 气泡靠头像定位，仅轻微覆盖边缘，不盖脸、不盖姓名/SVIP/统计，也不额外撑出一整行巨大头部空白。尾巴与主体相连，不留一颗明显断开的白色圆块。
4. 空状态显示小“＋”，不要显示占满空间的长占位句；点击进入状态编辑。有状态时显示短文字/表情，最长内容采用受限预览，点开完整内容编辑，不随字数无限放大。
5. 保留预览后保存、清空、刷新持久化。简单按压反馈即可，不增加永久大幅漂浮动画。
6. 验证无内容、短句、长句、表情及长名字，在360/390/430宽度均不过界、不推挤资料。

六、书友圈发布入口越界
现象：顶部头像、搜索框、黑色发布按钮排在一行，发布按钮右半截被屏幕裁掉。
1. 顶部容器宽度取应用可用宽度，不写死超过小屏的总宽。头像与发布按钮尺寸受控，搜索区域可收缩；检查flex子项最小宽度、gap、padding和按钮文字。
2. 首选发布按钮完整显示在同一行；极窄布局可用清晰图标入口或将搜索放下一行，但仍明确可发现且触控可用。不能通过overflow:hidden把按钮截掉来掩盖。
3. 主页面不得横向滚动；搜索输入、发布及排序入口均完整可点。键盘出现时顶部和编辑面板保存/发布操作仍可达。

七、删除和选项选择：使用项目自己的面板
用户不接受浏览器风格删除确认、选择界面；截图排序面板的字体偏小、空白巨大，视觉不统一。不要凭截图认定它一定是原生select；查实现后统一重做。
1. 删除使用书房自有确认弹窗：明确对象，提供取消和删除；删除后列表与相关计数同步，取消不改数据。不要用window.confirm/alert/prompt处理这些业务交互。
2. 排序“默认/最新/热门”优先使用紧凑锚点菜单；需要底部面板时高度随三项内容适配，不做占半屏的巨大空白列表。使用清晰标签、选中勾、舒适触控区域，无意义的每行箭头移除。
3. 选择立即作用于真实排序，取消保持原选择。按当前页面可见范围定位，菜单不能被父级overflow或Dock裁掉。
4. 按钮、文字、边框、阴影与新主题统一；关闭、遮罩、返回行为合理。键盘和其他弹窗同时存在时不叠成不可操作的多层界面。

八、书友圈布局重做，避免“大圆角卡片堆叠”
现象：上方搜索与两排分类占据很大区域，正文是一张张大白色厚圆角卡片；层级与重点不清楚。不是只换颜色，而是重排论坛信息密度。
1. 页面仍叫书友圈。顶部简洁搜索与发布；推荐/关注为主导航，当前项用短下划线或适量分类色突出。全部/书评/讨论为次级筛选，排序是次要入口；不要将每组都做巨大胶囊栏。
2. 论坛主体纯白、采用连续内容列表。帖子以细分隔线组织，减少外层厚边框、大圆角、大阴影与卡片之间过量空隙。必要的书籍引用/图片预览可保留轻量嵌套块，不把正文再套多层卡片。
3. 作者行：统一头像、紧邻姓名与时间；身份标记低调。正文为视觉重心，标题与内容区分，长正文适度折叠，展开后论坛可以滚动。
4. 书籍引用：书名、作者或封面整齐组合，点击能进入真实书籍；不要重复多层书名号。下方互动行统一点赞/评论/分享/已有礼物功能，图标与数字同行，计数必须真实。
5. 分类用清晰含义和重点色，不添加假热榜、假置顶、假人数。“AI”身份可保留真实标识，但禁止随意把系统功能图标改为emoji；已有用户/NPC头像素材不强制替换。
6. 删除、屏蔽等次要管理项收进更多菜单，不在每帖右上并排永久堆着X与禁止符号。保留所有既有权限与功能，自己帖子与他人帖子菜单不同。
7. 论坛允许垂直滚动；其他主页面尽量一屏完整显示，长设置进入二级页或局部滚动。底部Dock与安全区要预留，最后一条内容及操作不能被遮住。
8. 原有剧透打码、进入论坛警告、帖子中央详情、评论回复折叠继续有效。个人主页点击自己的动态仍在当前页面中央打开，不跳到书友圈。

九、文风故障：先核查已知链路，不编造用户尚未提供的具体表现
用户明确表示发现文风bug，但本轮尚未给出具体输入、输出或截图。做可验证的接入检查，不凭想象重写所有文风，不声称已解决用户尚未描述的故障。
1. 核对文风展示名称、唯一ID、完整规则正文、选择保存、刷新恢复、写作请求实际传递的styleId，以及后端解析匹配。
2. 核对切换文风后下一次写作使用新文风；没有设置时按正确默认；不能出现不同名字共用空规则、只改变UI名字、旧缓存覆盖或缺失规则仍显示成功。
3. 核对书房AI与角色卡AI写书均使用正确文风；写作世界书先约束设定，再叠加文风。写作世界书仅用于书房AI/角色卡AI写书、续写和改写，不扩散到全局聊天或论坛NPC。
4. 不擅自新增此前因来源条件未纳入的潮声、旧雨、R09等资料，不把原作者限制抹掉或只改名字后使用。已存在的授权内容与原创“余温”保留。
5. 用同一短写作任务对已内置文风做请求组装检查；真实模型测试需在已有可用配置下控制调用次数，不批量跑整套大文档。没有可用配置时记录待验。
6. 输出具体检查结果及可复现接入错误。用户后续补充文风现象时作为追加任务，不要求重传整个资料包。

十、完成与上线验收
执行顺序建议：联网诊断与完整内置书库 → 分享数据读取 → 气泡/发布越界 → 主题与论坛 → 文风接入核查。
1. 进行本轮相关类型、lint、更新检查与有意义的功能验证。不要通过any、禁用规则或吞错误假装修好；原有无关错误与新增错误分开记录。
2. 本机此前因内存不足崩溃，不反复调大heap重跑完整构建，也不要求用户反复关闭软件才能继续。使用现有云端构建路径验证，云端编译失败则定位修复。
3. 对360/390/430宽度检查截图或浏览器实际布局，重点：气泡有效尺寸、发布按钮完整、论坛最后一条可点、菜单可达。无法截图如实说明，不能把代码阅读叫实机验收。
4. 分享与联网问题不仅检查函数是否存在，要记录实际请求结果和内容读取结果。内置书库逐本列来源和完整性情况。
5. 同步主项目与书房各自的真实更新日志及通知入口。两个应用版本号可不同，但同批更新要对应一致。使用当前版本递增，不写死历史版本；未验证内容标待确认，不能写全修复。
6. 完成正常提交/合并/推送后，查询Vercel Production构建状态、实际提交SHA及正式域名的新发布标识/资源，不只看首页200。生产失败不能报告上线成功。
